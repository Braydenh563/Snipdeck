## Blocked / v1.1
- Windows code unverified at run time
- Dropped files are now read on a worker (`drop_read.rs`, chunks of about 64 MiB, stored on the UI thread chunk by chunk); there is still no progress toast (a new string would touch the catalogs). Storing (hash + blob write) stays on the UI thread because the store is not `Send`.
- Per-tab drop: NOT shipped. Checked in leftovers pass (winit 0.30.13, Slint 1.18.1):
  - What is possible without forking winit: winit registers its own `IDropTarget` once, in `Window::new`
    (`platform_impl/windows/window.rs:1194`, `RegisterDragDrop`) and only calls `RevokeDragDrop` on destroy
    (`event_loop.rs:1262`, harmless if ours replaced it). So `RevokeDragDrop(hwnd)` then `RegisterDragDrop(hwnd, ours)` on the
    UI thread (the thread that ran `OleInitialize`) is possible. winit's handler ignores the drop point (`_pt`), ours gets it.
  - Why it is not shipped: (1) the point has to become a tab. Slint exposes no tab rectangles to the host (tab widths follow
    their text, the strip scrolls) and the OS drag never reaches Slint, so it needs either a geometry export from
    `ListTabBar` or a synthesised pointer move plus a `hover-index`; both are UI changes that can only be judged on a real
    Windows run. (2) Replacing winit's target means our code owns every Panel file drop, including `HoveredFile` /
    `DroppedFile` equivalents, a COM object with `unsafe` that cannot be built-and-run here; a mistake loses the drop that works
    today (itself unverified on Windows). (3) The decision logic alone (point + rectangles to index) is trivial and would be a
    half version without (1).
  - To do it: add `ListTabBar` geometry (or hover-index), export it per frame, add `windows/drop_target.rs`
    (`#[implement(IDropTarget)]`, DragOver gives client-physical point via `ScreenToClient`), portable `tab_at(rects, point)`,
    controller `drop_create(.., Some(list))` already takes the list, and a `tools/windows-test` wizard step; the owner verifies on Windows.
