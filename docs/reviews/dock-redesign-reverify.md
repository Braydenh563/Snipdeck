# Dock redesign re-verify (dd3227c)

Re-check of the 35 findings in dock-redesign-review.md against dd3227c. 27 fixed; finding 31 refuted on re-check. Items still open or new, each confirmed by an independent refuter, numbered R1-R15:

R1 [major] New (dd3227c): a full-screen app on ANY monitor stops hover reveal on the dock and drops its tab below other windows
Evidence: dock_tick sets `self.fullscreen = self.target.fullscreen_in_front()` (dock_ctl.rs:272). When `dock_covered()` (fullscreen && !panel_focused), it sends `HandleHover(false)` whatever the cursor does (dock_ctl.rs:273-281). topmost() also turns false (controller.rs:854-863). The Windows implementation is `SHQueryUserNotificationState()` matching QUNS_BUSY, QUNS_RUNNING_D3D_FULL_SCREEN or QUNS_PRESENTATION_MODE (snipdeck-platform/src/windows/target.rs:830-837). That is a session-wide state, not per-monitor, and nothing compares it with the dock's monitor. Owner path: a full-screen video or game on monitor 2 while working on monitor 1, where the Panel is docked. Every tick then forces HandleHover(false), so pointing at the tab never reveals. The tab also loses topmost and sinks under the maximized windows on monitor 1, so it cannot be seen or clicked; only the hotkey brings the Panel back. This is exactly the owner's 'it doesnt show when I want it or hover my mouse near it'. The tests at controller/tests/dock.rs:1765 and :1788 use a single display, so they cannot catch it. Inferred from code and the API's documented global scope; not run on Windows.
Fix: Only treat the dock as covered when the foreground window is full-screen on the dock's own monitor: compare GetForegroundWindow's monitor, or its rect against the monitor rect, with self.monitor. Alternatively, pass the monitor id to fullscreen_in_front(). Add a controller test with two displays: full-screen on the other display, and the tab still reveals and stays topmost.

R2 [minor] New (fd36ac6): a dock on an edge shared with another monitor now has only a 6 px reveal target that the cursor does not stop at
Evidence: Before the fix, `near(cursor, tab, 12)` reached 12 px past the tab on both sides, a band about 30 px wide that also extended onto the neighbouring monitor. on_tab (frame.rs:549-562) now requires `across` inside the 6 px tab (9 px at 150 %). On an outer screen edge the cursor clamps, so slamming the mouse there works. Docking is not refused on an edge shared with another monitor: Monitor (frame.rs:33-43) has no neighbour information, and edge_at only takes the work area and the taskbar. So a Right dock on the left monitor of a side-by-side pair is reachable, and there the pointer runs straight through the strip into the next monitor; hover reveal then needs a precise 6 px stop. Inferred from code; not run on Windows.
Fix: For an edge with a neighbouring monitor, also count the pixels just past the edge (on the neighbour) as on the tab. Alternatively, refuse or warn about docking to an inner edge. Add a test with a second display adjacent to the docked edge.

R3 [minor] Finding 13: full-height bloat regression tests deleted; old full-height docks open as full-screen top or bottom docks
Evidence: The three controller tests are restored and updated: `moving_a_side_dock_to_the_bottom_does_not_bring_the_full_height_along` (tests/dock.rs:1355), `a_stored_bottom_dock_that_was_saved_full_height_reopens_at_the_panel_height` (:1392, expects 480), and `an_old_full_height_side_dock_opens_compact_when_the_full_edge_is_off` (:1416). The frame.rs unit tests `an_old_full_height_side_dock_is_compact_when_the_full_edge_is_off` and `a_top_or_bottom_dock_is_never_as_tall_as_the_screen` are also back. Reverting `frame::dock_size` would fail the bottom-reopen and legacy-side tests. Both of the finding's docked cases now hold: an old left dock moved to the bottom gets the floating height, and an old `{edge:bottom,h:1040}` with no pre_dock opens 480 tall through `dock_open`→`dock_size`. Not fixed is the second half of the scenario: 'undocking gives a full-height floating Panel'. An old entry with no `pre_dock` keeps `w h` = the docked frame as its floating size (settings.rs:1176-1185 only moves pre_dock). This includes the old SPEC default `{edge:right,w:320,h:1040}` (settings test at settings.rs ~1632). So `dock_to(None)` (dock_ctl.rs ~553, `floating = clamp(Rect::of(&geometry))`) and a drag pull-off (`sizes.floating`, dock_ctl.rs:532) both give a floating Panel as tall as the work area. No test covers undocking such an entry.
Fix: In the migration (pre_dock absent, edge set, h at or near the work-area height) or in dock_to(None)/drag Float, apply the same cut to the floating size as dock_size does: the default height, capped at work.h/2. Add a test that undocks an old `{edge:right,h:work.h}` entry and expects a non-full floating height.

R4 [minor] New: a legacy full-height side dock opens compact but a drag shows and stores it full height
Evidence: `frame::dock_size` treats a side size as legacy, and cuts it, only when `along.is_none()` and full_edge is off (frame.rs:374-375). `dock_open` passes `geometry.along` (dock_ctl.rs:183), so a migrated `docked=(340,1040)` with no along opens 480 tall. `sizes_on` passes `Some(0)` for the side size (dock_ctl.rs:534), which turns the legacy cut off. So a press-and-slide along the edge, or a drag to either side edge, previews at 1040 (dock.rs:401-414 via `docked_on`). `drag_end` then stores `docked=(340,1040)` with an `along` (dock_ctl.rs:755-765), which makes the full height permanent and no longer legacy. On Windows this happens only if no Resized report has already rewritten the docked size after the compact placement (panel.rs:782-790 stores place.h on a resize report). That depends on the host and is unverified here. No test drags a legacy full-height side dock.
Fix: In sizes_on, pass the stored `geometry.along` for the side size (as dock_open does), or have the migration/first placement write the cut size back. Add a test: an old full-height left dock with no along, press and slide on it, and the preview stays 480 tall.

R5 [minor] Finding 9: a resize in progress is not counted as 'held'
Evidence: panel.rs:700 sets self.resizing = true when resize() returns ResizeWindow. dock_held (dock_ctl.rs:194-201) holds while resizing and clears the flag on the first tick where primary_down() != Some(true). Test a_resize_under_way_holds_the_docked_panel_out (tests/dock.rs:1656) fails on revert (it collapses after 400 ms). Gap: the hold depends on GetAsyncKeyState reading 'down'. In finding 6's own scenario, an elevated foreground Target with the Panel WS_EX_NOACTIVATE so the Target stays foreground, primary_down() is Some(false). The flag is cleared on the first 50 ms tick, and the mid-resize tuck still happens there. Where the button cannot be read (None) the flag also holds nothing. No test covers the Some(false)-while-resizing case.
Fix: Clear `resizing` on the window's own end of the size loop (WM_EXITSIZEMOVE, or the next frame_changed after the resize) and not only on a polled button-up. Or apply the seen-down rule from drag_let_go: drop the flag on Some(false) only after Some(true) was seen. Add a test with primary_down Some(false) throughout a resize.

R6 [minor] Finding 16: resize not counted as held (duplicate of 9, win32 lens)
Evidence: Same code as finding 9: panel.rs:700 and dock_ctl.rs:194-201. Fixed for the normal case, with test tests/dock.rs:1656. Under an elevated foreground window (GetAsyncKeyState fails and reads as up) the flag is dropped at once, so the tuck in the middle of the OS size loop described here still happens.
Fix: As for finding 9.

R7 [minor] Finding 28: release safety net untested; test double cannot report the button; drag_cancel untested
Evidence: FakeTargets now has set_primary_down and a primary_down impl (host.rs:410-413, 463-465), and drag_let_go is covered both ways (tests/dock.rs:1525, 1549). drag_cancel (dock_ctl.rs:808) still has no caller anywhere: a grep of crates/ finds only its definition. It is still dead code with no test, so the 'window went away' cancel path the review mentions is still not wired up or tested.
Fix: Either wire drag_cancel to the host's window-gone or capture-lost path and test that it returns the remembered placement, or delete it (replace, do not layer).

R8 [major] NEW: a Panel docked to an edge shared with another monitor cannot be dragged straight onto that monitor
Evidence: dock.rs:439-447 never undocks on a push 'into' the edge, and drag_ctx (dock_ctl.rs:640-646) keeps the docked monitor for Slide. Take the fixture layout: display() at x 0-1919 and second_display() at x 1920+ (tests/dock.rs:87). A Panel docked Right on monitor 1, pressed at (1700,110) and dragged right to (3000,500), gets away = -1300. It stays in Slide on monitor 1's right edge, sliding up and down, and drag_end docks it there again. The user has to pull it 24 px or more back toward the middle of the screen before it will cross to the other monitor. edge_at (frame.rs:520) excludes only the taskbar edge, so inner seam edges can be docked, and the kebab can choose them as 'nearest'. Both cross-monitor tests (tests/dock.rs:1055 and the new :1737) pull left to 1600 first, so they hide this. Owner: 'it always seems to want to be docked'.
Fix: In Slide, also undock when the cursor leaves the docked monitor (monitor_at(cursor).id != docked monitor id), or when it is pushed past the work-area edge by more than UNDOCK_PULL. Add a test that drags a Right dock straight right onto second_display() and asserts Floating there.

R9 [minor] NEW: no corner hysteresis before arming; a near-diagonal wobble at a corner restarts DOCK_ARM
Evidence: dock.rs:472-480 keeps `since` only while edge_at returns the same edge, and edge_at picks the smaller gap (frame.rs:520-532). Near a corner, positions such as (2,1)->Top and (1,2)->Left alternate, and each flip restarts the 200 ms wait. Arriving along the top into the exact corner (0,0) flips to Left on the tie and restarts it as well. The new test (dock_drag_tests.rs:323) encodes 'never 200 ms at either' as intended behaviour. This is the mutation finding 30 named as the cause of 'can't drag to a corner'. The Float window does not jump, but the dock offer can be delayed for as long as the hand wobbles. Severity depends on real cursor jitter on Windows, which is unverified.
Fix: Keep the held edge (and its `since`) while the cursor is still within EDGE_ZONE of it, even if another edge is nearer. Switch only when it leaves that edge's zone. Change the corner test to wobble inside both zones and expect Preview of the first edge at t=200.

R10 [minor] NEW: same-scale monitors with different floating sizes now resize the window mid-drag at the seam, and flip it on a wobble
Evidence: resized_under (dock.rs:518-521) is also true when only the stored floating size differs, with no scale change. Every step where the cursor crosses the seam then runs float() and Places the window at the other monitor's size (:461-466). A cursor wobbling across a seam swaps the size, and the cursor's grab ratio with it, on each crossing. Before the fix the size changed only on release. No test covers a wobble at the seam. This fits the owner's 'spasming' report on multi-monitor setups.
Fix: Re-measure mid-drag only on a scale change, which Windows forces. Apply a size difference at the same scale on release, as before. Or add hysteresis: require the cursor to be some px into the new monitor before switching.

R11 [major] 32: tab always present after a hidden start and a tray hide
Evidence: The tray part is fixed. TrayEvent::TogglePanel now calls toggle() (controller.rs:1006, 866-876), so an open dock tucks to its tab and a tucked one opens. the_tray_click_tucks_an_open_dock_and_opens_a_tucked_one (tests/dock.rs:1850) would fail if this were reverted to hide().

The hidden start is NOT fixed in the real app. main.rs:467-485 calls window.show(), then restore_frame(&window), then Binding::start_hidden, all before run_event_loop_until_quit. Slint 1.18.1 creates the winit window only from an ActiveEventLoop: set_visibility only registers it as inactive (i-slint-backend-winit-1.18.1/winitwindowadapter.rs:1627-1633), and create_inactive_windows takes &ActiveEventLoop (lib.rs:633-646, called from event_loop.rs:109/242). So with_winit_window(monitor_of) returns None and restore_frame falls back to restore_anchor (main.rs:692-703). main.rs:700 says the same thing in its own comment. With no open_anchor (show() never ran), restore_anchor returns nothing (controller/panel.rs:820-823), so self.monitor stays None (controller.rs:481). dock_edge() needs the monitor (dock_ctl.rs:52-53), so dock_live() is false and Controller::start_hidden (controller.rs:880-886) takes the hide() branch. The window is created hidden, no tab exists, and the owner still gets nothing at the edge after login.

The controller test a_hidden_start_of_a_docked_panel_shows_its_tab (tests/dock.rs:1819-1846) passes only because it calls restore_frame(&display()) with a real monitor first, which startup cannot do. No test covers the main.rs wiring.

Second gap: starts_tucked() is true if ANY monitor's geometry has an edge (controller.rs:891-898), but start_hidden decides on the window's own monitor. On a multi-monitor setup docked on a secondary display it would hide anyway.

Stray window or focus at login, as the code stands: no. hide() runs before the loop, so the window is created with visible=false. The HidePanel effect, newly applied at login, calls host.release(), which is only end_text_entry (platform.rs:120-121). If the decision were deferred until the window exists, the window is created with with_active(false), i.e. SW_SHOWNOACTIVATE (main.rs:899, window_style.rs:3-4), so it would not steal focus. It could flash the full Panel for a frame before the tuck. Unverified on Windows.
Fix: Make the start-hidden decision once the native window exists, with a known monitor. Run restore_frame(monitor_of) and then start_hidden from the attach_when_created callback or from a zero-delay timer after the loop starts, keeping the window hidden until the handle placement is applied. Alternatively, seed self.monitor from the stored docked geometry's monitor through TargetSource before calling start_hidden. Add a controller test where start_hidden runs with no prior restore_frame (monitor unknown) and still tucks or defers. Make starts_tucked and start_hidden agree on which monitor counts.

R12 [minor] Finding 18: Settings and onboarding text no longer match dock behaviour
Evidence: Most of the text is rewritten. settings.slint:879 now says a docked Panel tucks only after a paste, which matches dock_after_use (dock_ctl.rs:327-336). settings.slint:955 says Off 'shows and hides like a floating one', which matches dock_active()=false, so hides_on_blur at controller.rs:1074-1090 applies. settings.slint:929 has the new 'Dock to' text, and 969/987 now say 'tab' and 'tucks'. The onboarding hint at onboarding.slint:386 now says it tucks into a thin tab; for a new install that is true because the default trigger is Both (settings.rs:241). Still wrong: (a) settings.slint:893 says 'a docked panel tucks into its tab instead' on blur, but with the trigger at Off a docked Panel has no tab and hides completely (controller.rs:1078 `!self.dock_active()`). (b) The option is still labelled 'Off' (settings.slint:959), while docs/reviews/dock-redesign.md:101 and the comments at settings.rs:1622/1656 call it 'Stay open'; the review asked for the rename. (c) docs/SPEC.md:72 still says the first run is 'docked to the right edge, full height ..., auto-hide off', which contradicts the new onboarding hint. No text test covers the wording, but the settings and onboarding goldens do, and they were not regenerated (see the new problem below).
Fix: Make the blur line conditional or reword it: 'a docked panel that tucks goes to its tab instead'. Rename Off to 'Stay open', or change dock-redesign.md:101 and the settings.rs comments to 'Off'. Update SPEC.md:72 to the current first-run default (Both, not full height).
