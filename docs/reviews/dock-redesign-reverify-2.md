# Dock redesign re-verify, round 2 (771b44b)

R1-R5, R7-R11, R13-R15 fixed. Open: R6 (partial), R12 (partial), and four sweep findings that refuters could not refute (one major). fullscreen_in_front was removed in 7b894bf. Read-only check, no cargo run; Windows behaviour unverified.

## R6 (partial, minor)
Evidence: R6 is now partly fixed, at 771b44b, on the same code as R5. resize() (controller/panel.rs:700-702) sets resizing = true, resize_button_seen = false and resize_at = now. remember_frame (panel.rs:729-731) moves resize_at forward on each resize report while resizing. The host sends those reports from main.rs:744-763, one per winit WindowEvent::Resized. dock_held (controller/dock_ctl.rs:198-203) calls resize_goes_on (dock_ctl.rs:211-224). Some(true) marks the button as seen and holds. Some(false) after the button was seen ends the hold. Some(false) with the button never seen holds while now - resize_at < RESIZE_QUIET_MS, which is 1000 (dock_ctl.rs:33). None holds nothing. On Windows primary_down is always Some(GetAsyncKeyState high bit) (platform.rs:88-90, snipdeck-platform/src/windows/screen.rs:49-56).

So in the elevated-foreground case the flag is no longer dropped on the first tick. A resize that keeps changing the size stays held. Test a_resize_holds_the_dock_out_where_the_button_always_reads_as_up (controller/tests/dock.rs:2172-2214) covers this. It reads primary_down Some(false) throughout, sends frame_changed every 200 ms and expects no tuck for 2 s. That test would fail if the quiet rule were reverted to "Some(false) => false", because the panel would tuck about 450 ms in. Test a_resize_under_way_holds_the_docked_panel_out (dock.rs:1656) still covers the normal case.

Residual: the hold now depends on size reports, not on the end of the OS size loop. The required fix proposed WM_EXITSIZEMOVE or the seen-down rule; WM_EXITSIZEMOVE is used nowhere outside paint_diag.rs:237-238. A size loop that runs on with no change in size sends no Resized, so after 1 s the hold drops, and after the 400 ms leave delay (dock.rs:1672-1676 shows 400 ms) the panel tucks in the middle of the loop. The clearest case is a pull past the width limit: panel.slint:192 sets max-width 480px, so the OS clamps the window and no further Resized arrives. Take a Right dock under an elevated foreground window. Pull its left grip past 480 px wide and hold still for about 1.4 s with the pointer out past the panel. The dock tucks during the size loop, which is the finding-16 scenario. No test covers a hold with no size reports, such as one stopped at the clamp. This is inferred from the code; I did not run it on Windows.
Remaining: The hold should end on the window's own end of the size loop (WM_EXITSIZEMOVE from the host, or the WM_SIZE that follows it), not when 1 s passes with no size report. Then add a test: primary_down Some(false) for the whole resize, the cursor past the widest the panel goes, no frame_changed for more than 1.4 s, and expect no tuck until the end-of-resize signal. Until the owner runs it on Windows, also list it as Windows-unverified, since the premise (GetAsyncKeyState reads up under an elevated foreground window) is not verified.

## S: First show after a non-tucking --hidden start uses the monitor cached at launch, which may be gone by then [major] crates/snipdeck-app/src/controller/panel.rs
Evidence: controller.rs:893-895: `start_hidden` calls `self.find_monitor()`, which sets `self.monitor`, even when the Panel then hides (a floating Panel, or a dock with trigger Off), and `unplaced` stays true. panel.rs:833-835 (`restore_anchor`, unplaced branch): `let known = self.monitor.clone(); return match known.or_else(|| self.find_monitor()) { Some(monitor) => self.restore_on(&monitor), ...}`. `find_monitor`, which checks that the monitor still exists (dock_ctl.rs ~540, `.filter(|m| m.id == g.monitor_id)`), only runs when nothing was cached. Nothing refreshes `self.monitor` while the Panel is hidden: there is no display-change handler, and `dock_tick` only runs while `dock_live`.
Scenario: The startup task launches Snipdeck --hidden at login with the laptop docked, and the Panel was last left floating on the external monitor (x around 2400). The user unplugs the monitor, then presses the Panel hotkey. ShowPanel calls restore_frame; monitor_of returns None because the window does not exist yet, so restore_anchor runs. It calls restore_on(stale external monitor), which emits PlaceWindow at the external monitor's coordinates. Slint stores these as the pending creation position, so the window is created where no monitor exists. At best it appears and then jumps when the first Resized clamp runs; at worst it stays off-screen until "Reset size and position". Windows-unverified.
Fix: In the unplaced branch, always ask the host again (`self.find_monitor()`) rather than trusting the monitor cached at start, or have start_hidden's non-tucking branch leave `self.monitor` unset. Add a test: start_hidden with two monitors, remove the one the Panel was left on, then call restore_anchor and expect a placement on a present monitor (or none).
Verifier: I could not refute it. The code path is real and nothing handles it at 771b44b.

1. When `start_hidden` runs and nothing is cached, it calls `self.find_monitor()` (controller.rs:893-895). `find_monitor` sets `self.monitor` as a side effect (dock_ctl.rs:546). The function then hides the Panel (controller.rs:900) and leaves `unplaced` true. `unplaced` is set true at controller.rs:494 and is cleared only at controller.rs:897 (the tuck branch), panel.rs:839 and panel.rs:872.
2. Nothing refreshes `self.monitor` while the Panel is hidden and has no window. It is assigned only at panel.rs:746/854/871 and dock_ctl.rs:230/546/863. Those are frame reports, restores and dock moves, and none of them runs before the first show. `show()` (controller.rs:904-925) reads no monitor unless the dock is tucked, and `on_target_changed` (controller.rs:1041) only updates the Target.
3. On the first show, `Effect::ShowPanel` calls `restore_frame(&window)` (main.rs:654-656). With no native window yet, `monitor_of` returns `None`, so `restore_anchor` runs (main.rs:694-705). The comment at main.rs:702 states this is the intended `--hidden` path.
4. With "Panel opens: where you left it", `open_anchor_now` returns `None` (dock_ctl.rs:427), so `restore_anchor` takes the unplaced branch (panel.rs:833-835). There, `known.or_else(|| self.find_monitor())` uses the cached monitor whenever one is set. The check that the monitor still exists (`.filter(|m| m.id == g.monitor_id)`, dock_ctl.rs:542) is skipped. `restore_on(stale)` then emits `PlaceWindow(placement(stale))`, which is fitted to the stale monitor's own work area and so keeps the gone monitor's coordinates.
5. `PlaceWindow` is applied before the window exists. main.rs:465-467 relies on exactly that ("the window is made there"), so the window is created at the gone monitor's coordinates.

There is no test for this. The `--hidden` tests (controller/tests/dock.rs:1836-1930) never remove a monitor between `start_hidden` and the first show.

What happens next is worse than the finding says. `frame_moved` → `remember_frame(..., resized=false)` (panel.rs:715-721) stores a system-reported position without clamping. The `is_parked` guard only catches minimised frames, and x=2400 is not one. So if Windows reports a Move for the off-screen window, the off-screen frame could be stored as the place for whatever monitor `monitor_of` returns, and later shows would reuse it.

Not verified: how Windows actually creates the window at a position no monitor covers, and whether the first Resized clamp brings it back on screen. That is Windows-only behaviour the owner has to run.

The suggested fix fits: in the unplaced branch, call `find_monitor()` again instead of trusting the cached monitor, or have the non-tucking branch of `start_hidden` leave `self.monitor` unset.

## S: Legacy full-height dock fix is bypassed when the Panel is dragged to another monitor (and when an old docked-only full size is undocked and re-docked) [minor] crates/snipdeck-app/src/controller/dock_ctl.rs
Evidence: geometry_on (dock_ctl.rs ~520-534) shrinks an old entry (edge Some, along None, h >= work area - 2) to the default height and says "Whatever is stored from it next (a slide, a resize, an undock) keeps that". But drag_end's update for the monitor the Panel left (dock_ctl.rs:851-858) rebuilds that entry from the raw stored value: `PanelGeometry { edge: None, along: None, ..g.clone() }`. It keeps h = full work-area height and drops `edge`, so geometry_on no longer recognises it as old. Separately, dock_to(None) (dock_ctl.rs:649-651) keeps `docked: Some((w, full))`. A later dock_to(Some(edge)) calls dock_size with along Some(..), which is not treated as legacy, and returns the full height again.
Scenario: (a) A settings file from an older version has the Panel docked Right on monitor A, stored as x=1600, h=1040, no along. The user drags it straight across the shared edge onto monitor B (the new a_dock_on_an_edge_another_monitor_begins_at_drags_straight_onto_that_monitor flow). A's entry becomes floating with h=1040. If the Panel is later dragged back to A, or B is disconnected so placement() falls back to A, it opens as a floating Panel as tall as the work area. (b) A file with `docked: [340,1040]`, edge Left and no along: undocking from the menu, then "Dock to the left edge", docks it full height again although the full-edge setting is off.
Fix: In drag_end's `left` update, start from `self.geometry_on(old)` (or apply the same height correction) instead of `g.clone()`. In dock_to(None) (and the drag undock), drop or correct a docked size that is a full-height legacy value. Add tests for both paths next to undocking_a_dock_an_older_version_stored_full_height_gives_a_panel_of_ordinary_height.
Verifier: I could not refute the finding. Both paths are reachable at 771b44b.

(a) Drag to another monitor. `geometry_on` (dock_ctl.rs:522-534) only shrinks an entry that has `edge.is_some() && along.is_none() && h+2 >= area.h`. Nothing writes monitor A's entry during the drag. `remember_frame` returns early while dragging (panel.rs:733-736), and drag_begin/drag_move never call `update_settings` (the only calls are at dock_ctl.rs:662, 675, 844 and 882). So at drag_end the `left` update (dock_ctl.rs:849-859) rebuilds A's entry from the raw stored `g`: `PanelGeometry { edge: None, along: None, ..g.clone() }`. That keeps h=1040 and drops `edge`, so the legacy shape is gone. When the Panel comes back to A, `geometry_on` no longer corrects it, and `placement` (panel.rs:817-819) gives `frame::clamp(Rect::of(g))` for `edge` None. The result is a floating Panel as tall as the work area. The legacy input shape is exactly the test fixture `old_full_height_dock` (tests/dock.rs:2060-2075). The existing cross-monitor test (tests/dock.rs:2026-2056) only checks that `edge` is None and never checks the height.

(b) Undock, then dock again. `Settings::sanitize` (settings.rs:1176-1186) turns a c21d425-era file into `docked = (w,h)` plus floating `w h = pre_dock`, and keeps `along` None. c21d425 does write such a file: when the Panel moves to another edge, its dock_to gives `along` None, and with `full_edge` on it stores the full-height frame together with `pre_dock`. In the current version, `dock_to(None)` (dock_ctl.rs:648-652) keeps `docked`. `remembering` (settings.rs:87-99) pushes no `other_along` because the old `along` was None. A later `dock_to(Some(Left))` therefore computes `along` from the floating frame, which is `Some(..)` (dock_ctl.rs:619-631). In `frame::dock_size` (frame.rs:376-378), `legacy` is then false and the function returns the stored full-height `docked` size unchanged. With `full_edge` off, the Panel docks at full height again.

Neither path is handled or tested. The fix the finding suggests (start the `left` update from the height-corrected geometry, and correct a full-height `docked` size when undocking) is sound.

## S: Docs still describe full-screen handling as "in front" and the hidden start as already placed [minor] docs/SPEC.md
Evidence: SPEC.md:73: "while a fullscreen app is in front a docked Panel is not topmost ... the pointer at the screen edge does not reveal it". docs/user-guide.md:331-332: "While a full-screen app is in front the tab stays out of its way". The code now checks only the Panel's own monitor, and also counts a full-screen window that is not in front (WindowFromPoint at the monitor's middle, target.rs ~865-875). SPEC.md:54 was updated ("under a full-screen app on its own monitor"), so SPEC now contradicts itself. binding.rs:247-250 documents `start_hidden` as "The app started with the Panel not shown and its window has been placed", but main.rs:464-469 now calls it before any window exists or is placed. binding.rs:241-245 says restore_anchor only places at the mouse or caret, but it now also restores the last place on the last monitor.
Scenario: A user with a full-screen video in front on monitor 2 reads the guide and expects the tab on monitor 1 to step aside, but it stays topmost and reveals. A developer reading binding.rs assumes the window is already placed when start_hidden runs and reorders main.rs accordingly.
Fix: Change SPEC.md:73 and user-guide.md:331-332 to "while a full-screen app covers the Panel's monitor". Update the binding.rs doc comments for start_hidden (window not yet made; the controller finds the last monitor and places the tab) and restore_anchor (also the first placement where the Panel was left).
Verifier: I could not refute it; every claim checks out at 771b44b.

1. **SPEC.md contradicts itself.** SPEC.md:54 says "always on top except under a full-screen app on its own monitor". SPEC.md:73 still says "while a fullscreen app is in front a docked Panel is not topmost ... the pointer at the screen edge does not reveal it".

2. **The code checks the Panel's own monitor, not "in front".**
   - controller/dock_ctl.rs:298 calls `target.fullscreen_on(monitor)`.
   - platform.rs:96-103 passes the middle of that monitor's work area to `fullscreen_covers`.
   - target.rs:844-876 counts the foreground window or the window found by `WindowFromPoint` at the monitor's middle. Its own doc says this covers a video on a second screen even when it is not in front.
   - So a full-screen app in front on another monitor does not step the tab down, and one that is not in front on the Panel's monitor does.

3. **user-guide.md:331-332 is stale too.** It says "While a full-screen app is in front the tab stays out of its way", the same old wording as SPEC.md:73.

4. **The `start_hidden` doc in binding.rs:247-248 is wrong.** It says "its window has been placed". But:
   - main.rs:464-468 says the controller places the tab before the window is shown, then calls `Binding::start_hidden`.
   - controller.rs:888-897 says the Panel "has no window" at that point, and calls `find_monitor` itself.

5. **The `restore_anchor` doc in binding.rs:241-242 is incomplete.** It only mentions the mouse or text cursor. controller/panel.rs:823-837 shows it also restores the place where the Panel was left, on the last monitor (the `unplaced` path through `find_monitor` and `restore_on`), even without an anchor.

These are doc-only problems, so the "minor" rating is right. Commit 6ed1fbb ("per-monitor full-screen check") changed the behaviour without updating SPEC.md:73 or user-guide.md:331.
